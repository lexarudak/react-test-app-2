# Context (useContext, Context.Provider, Context.Consumer)

Context решает проблему передачи данных между компонентами. Мы можем создать контекст:

```ts
const Context = createContext(fallbackValue)
```

Context - объект, который возвращает Provider и Consumer. Consumer - старый способ получить контекст в компоненте. (ну и для классовых компонентов актуален) Provider - компонент-обертка. Он принимает проп value. В него нужно передать контекст, доступ к которому ты хочешь обеспечить изнутри. Потом в компонентах внутри этого Provider ты можешь вызывать useContext(Context) и получать к нему доступ.

fallbackValue используется когда компонент находится вне Provider - в этом случае useContext вернет именно это значение по умолчанию.

Context особенно полезен в компонент-композициях - когда нужно передать данные между "родительским" компонентом и его "детьми", не пробрасывая пропсы через промежуточные элементы. Это активно используется в UI библиотеках:

```ts
// Пример: Dropdown компонент
<Dropdown>
  <Dropdown.Trigger>Open menu</Dropdown.Trigger>
  <Dropdown.Content>
    <Dropdown.Item>Option 1</Dropdown.Item>
    <Dropdown.Item>Option 2</Dropdown.Item>
  </Dropdown.Content>
</Dropdown>

// Accordion, Modal, Tabs, Form - все работают по этому принципу
<Accordion>
  <Accordion.Item>
    <Accordion.Header>Title</Accordion.Header>
    <Accordion.Content>Content</Accordion.Content>
  </Accordion.Item>
</Accordion>
```

Внутри такие компоненты используют Context, чтобы Dropdown.Item мог общаться с родительским Dropdown, а Accordion.Content знал о состоянии Accordion.Item.

Оптимизация и лучшие практики
Provider сравнивает value обычным строгим сравнением через Object.is(). Так что каждый заново созданный массив, объект или функция будет триггерить ререндер всех чайлдов. В Provider реализован механизм как в memo: если prevValue === value, то ререндера не будет. Bailout. Поэтому надо мемоизировать value.

Лучше создавать несколько мелких контекстов вместо одного большого. Держать контексты нужно как можно ниже, чтобы оборачивать как можно меньше чайлдов. причем контксты могут даже одним стейтом управлять. один на чтение другой на запись, если они оборачивают разные чайлды

Когда использовать Context
✅ Стоит использовать для:

Редко обновляемых данных (theme, locale, user)
Простых значений
Локальных областей UI (модалки, формы, compound components)
Конфигурации и настроек

❌ Не стоит использовать для:
Больших данных с частыми обновлениями
Сложной бизнес-логики
Глобального app-level состояния с селекторами
Когда нужны middleware, devtools, time-travel debugging

## Почему Context не идеален для глобального стейта:

1. **Единственное значение** - при изменении любой части объекта ререндерятся ВСЕ подписчики
2. **Нет селекторов** - нельзя подписаться только на часть данных (как `useSelector` в Redux)
3. **Object.is() сравнение** - каждый новый объект в value триггерит обновления
4. **Нет ecosystem'а** - отсутствуют devtools, middleware, персистентность

Альтернативы
Для глобального состояния лучше использовать специализированные state менеджеры. Они хранят данные вне React fiber, имеют селекторы и не триггерят лишние ререндеры. Типа Zustand, Redux Toolkit или Jotai.

Из минусов Context - при изменении контекста ререндерятся **только компоненты, которые используют `useContext`**. React ведет внутренний список подписчиков и уведомляет только их. Компоненты без `useContext` НЕ ререндерятся при изменении Provider.value.

**Исключение:** если сам Provider компонент ререндерится по другим причинам (например, изменился его собственный state), тогда все children тоже ререндерятся - но это уже не связано с Context'ом, а с обычным поведением React.


```ts
const fallbackValue = {
  // будет доступно вне провайдера
  name: 'Valera',
  age: [25],
};

const parentValue = {
  // будет доступно внутри провайдера
  name: 'Parent Valera',
  age: [30],
};

const childValue = {
  // будет доступно внутри вложенного провайдера
  name: 'Child Valera',
  age: [5],
};

const ValeraContext = createContext(fallbackValue); // вот мы тут создали объект. в который потом ходим за его значением. провайдер по сути просто отвечает за то, какое значение там будет лежать. он просто в памяти храниться, не в файбере

const Parent = () => {
  const valera = useContext(ValeraContext);

  return (
    <div>
      {valera.name} - {valera.age}
    </div>
  );
};

const Child = () => {
  const valera = useContext(ValeraContext);

  return (
    <div>
      {valera.name} - {valera.age}
    </div>
  );
};

export const ContextApp = () => {
  return (
    <ValeraContext.Provider value={parentValue}>
      <Parent /> // использует parentValue
      <ValeraContext.Provider value={childValue}>
        <Child /> // использует childValue
      </ValeraContext.Provider>
    </ValeraContext.Provider>
  );
};
```

Контекст работает по принципу push - pop провайдера. при обходе дерева файбер (мы ведь из корня идем ) при входе в провайдер pushProvider кладет в СТЕК значение из пропса value. (до этого в стэке фолбек вэлью лежит. поэтому он виден даже то входа в провайдер откуда угодно) и потомки читают это актуальное значение из context._currentValue. когда доходит до следующего провайдера, то пушит его значение из вэлью в этот стек. и его потомки уже видят его. При выходе из Provider через popProvider восстанавливается предыдущее значение из стека, 
поэтому компоненты-сиблинги получают корректный контекст. ну а вне провайдер через юз контект мы получаем фолбек значенеи6 потому тчо только оно лежит в стеке. это нужно чтобы вкладывать одинаковые провайдеры друг в друга
