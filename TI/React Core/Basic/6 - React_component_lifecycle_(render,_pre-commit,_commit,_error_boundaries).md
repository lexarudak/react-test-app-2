# React component lifecycle (render, pre-commit, commit, error boundaries)

## 📍 Render phase (первый рендер)

- **Создаётся FiberRoot** — это объект-обёртка всего дерева.  
  В нём есть ссылка `current` на корневой Fiber, который почти пустой:  
  - `tag = HostRoot`  
  - `child = null` (ещё нет потомков)
  - служебные поля для связей и состояния.

- При вызове метода `.render(...)` начинается построение **work-in-progress** дерева Fiber:
  - Дерево строится по принципу: **один потомок (`child`) и цепочка соседей (`sibling`)** на одном уровне.

- Ещё на стадии компиляции весь JSX был заменён на вызовы функций `_jsx` и `_jsxs`.  
  Они создают **ReactElement** — обычный JS-объект вида:
  ```js
  {
    type: App,                  // сама функция-компонент
    props: {},                  // пропсы
    key: null,
    ref: null,
    $$typeof: Symbol(react.element)
  }
  ```

- Метод `.render(...)` получает этот ReactElement и:
  - Создаёт для него Fiber ноду (`tag = FunctionComponent`, если `type` — функция).
  - Заполняет базовые поля (`type`, `pendingProps`, `return`…).

- Вызывает функцию `App` (из `type`), передавая в неё `props`.

- В ходе выполнения тела функции:
  - React обрабатывает все хуки (`useState`, `useEffect` и т.д.).
  - Записывает их данные в связанный список `fiber.memoizedState`.
  - Получает возвращаемый JSX (ReactElement для следующего уровня).

- Когда `App` возвращает следующий ReactElement, React **строит Fiber** и для него.  
  - Так дерево строится рекурсивно до самого конца.

- В итоге часть узлов имеет `tag = FunctionComponent` (компоненты), а часть — `tag = HostComponent` (DOM-теги).  
  **Все HostComponent на первом рендере получают флаг `Placement` (`flags: 2`)** — этот флаг означает, что элемент **новый** и его нужно вставить в DOM в commit-phase.

## Более подробно на примере клика по кнопке

### Фаза клика
- браузер генерит событие клика
- рут элемент его отлавиливает общим слушателем
- запускает все онКлики от таргета до рута по цепочке
- у нас в хендлере был setState
- он генерит апдейт, кладет его в hook.queue.pending
- помечает узел и весь путь от него до рута как нуждающийся в обновлении (через childLanes)
- в taskQueue (это просто массив в памяти, обычный var) добавляется задача рендера
- в очередь задач добавляется schedulerCallback. функция, которая побежит по массиву taskQueue и начнет выполнять все, что там лежит
- когда до  рендера дойдет, то он запускается и старутет фаза рендера

```ts
[
  { callback: cleanupEffect1, priority: Normal },
  { callback: renderApp, priority: UserBlocking },    // ← наш render
  { callback: renderOtherComponent, priority: Low },
  { callback: runEffect2, priority: Normal }
]
```

### Фаза render WorkLoop запускает beginWork
- начинается обход дерева от корня к листьям
- если узел не нуждается в обновлении но при этом его чайлды нуждаются (childLanes) - идет к его чайлду и ВСЕ РАВНО СОЗДАЕТ  WIP ВЕРСИЮ ДЛЯ СЕБЯ из  alternate (копируя туда все из карента)
- если и узел не надо обновлять и всех его чайлдов fiber.childLanes == NoLanes, то бэилаут всего поддерева. и WIP не создается
у нас от корня до узлов с обновлениями будет создана новая ветка из WIPов. и когда мы дойдем до чайлда, который не изменился, эта ветка залинкуется на карент этого чайлда. ну или на сиблинга. Короче половина ветки будет состоять из WIPов и второая половина просто прикрепится из карентов тех узлов, что без изменения остались
Ну и все ченжи только в WIP происходят
- если файбер нуждается в обновлении то для функционально файбера вызывается его функция (компонент) с новыми пропсами из pendingProps
- выполняется код в теле компонента. Хуки применяют апдейты. Мы же на примере клика говорим так вот вызов нашего useState() в компоненте
-- переносит очередь апдейтов (у нас 1) из queue.pending в baseQueue
-- очищает queue.pending
-- применяет апдейты (высчитывает новое стояние). сохраняет его в memoizedState
-- возвращает новый массив [newState, dispatch]
- получаем новый реактЭлемент из метода return (там чайлды могли измениться)
Когда мы получили новый реактЭлемент, как результат выполнения компонента, начиначется фаза DIFF/RECONCILIATION. это часть beginWork. после того как она закончится - начнется новый beginWork для файбера, который будет построен для этого реактЭлемента.

DIFF/RECONCILIATION:
- тут мы стоим на WIP нашего файбер и сравниваем объект из current.child и новый реактЭлемент, полученный в результате выполнения функции компонента

1. у нас же вызов jsxs() возвращает реакт элемент типа
```ts
{
  type: Component,
  props: {
    children: [
      {type: "div", props: {}}, 
      {type: "p", props: {children: "hello"}}
    ]
  }
}
```
так вот DIFF превращает это в child -> sibling структуру. создавая  WIPы Для КАЖДОГО чайлда. Создает их по принципу:
Сравнение type и key:
- если они одинаковые, то строим WIP для текущего current.child и будет работать в нем
- если что-то отличается - помечаем старый файбер на удаление и просто строим новый WIP

После этого для каждого Чайлда и Сиблинга! идет Установка флагов. только для детей. Для внуков флаги расставит уже DIFF запущенный для первого чайлда в следующем кругу цикла
```ts
// Если создали новый fiber:
newFiber.flags |= Placement;  // нужно вставить в DOM

// Если переиспользовали, но props изменились:
wipFiber.flags |= Update;     // нужно обновить DOM props

// Если удалили старый:
oldFiber.flags |= Deletion;   // нужно удалить из DOM
```

2. Кроме того, если идет установка флагов для элементов списка. Если у нас есть список в котором элемнты поменялись местами, то начинается пересчет индексов. Тем элементам, что переехали "вправо по массиву" ставим флаг Placement. это оптимизирует ререндер
```ts
// Было: [A₀, B₁, C₂]
// Стало: [C, A, B]

// C₂ → позиция 0: старый индекс 2 > текущий lastPlaced (0) ✅ не двигаем
// A₀ → позиция 1: старый индекс 0 < текущий lastPlaced (2) ❌ Placement!  
// B₁ → позиция 2: старый индекс 1 < текущий lastPlaced (2) ❌ Placement!
```

3. Обновляются рефы (добавляются или удаляются если изменились)

После DIFF:
WorkLoop переходит к первому ребёнку и запускает для него beginWork → его DIFF → и так далее depth-first.

### completeWork
- тут мы идем обратно от листьев в корню
- функциональные файберы просто пропускаются
- для хост файберов если файбер новый - создется дом элемент (буквально document.createElement('div'))
- если файбер старый но пропсы изменились - готовит обновление пропертей в существующем дом элементе
- для новых хост файберов объединяет дом узлы в "ветки" (присоединяет чайлдов к родителю). эту новую ветку никуда не вставялет пока, просто в памяти лежит. просто через appendAllChildren собрали новые дом узлы в ветку
- в root.pendingEffects записываются все эффекты которые нужно будет сделать в коммит фазе. Чтоб заново дерево не обходить.  просто во время проходки от листьев к корню добавялем эффекты в root.pendingEffects

```ts
// В root fiber создаются списки:
root.pendingEffects = {
  placement: [divFiber, newSpanFiber],      // что вставлять
  update: [pFiber, existingDivFiber],       // что обновлять
  deletion: [oldButtonFiber]                // что удалять
};
```

```ts
// Готово к commit:
- WIP дерево построено ✅
- DOM узлы созданы в памяти ✅  
- Списки эффектов подготовлены ✅
- План изменений составлен ✅
```

## Commit фаза

0. ⚡ BEFORE MUTATION: (это раньше называли pre-commit фазой)
💾 Сохраняет важные вещи:
- Какой элемент сейчас в фокусе
- Что выделено мышкой (selection)
🧹 Вызывает cleanup:
- componentWillUnmount()
- useLayoutEffect cleanup
- getSnapshotBeforeUpdate()
🔇 Отключает события (чтобы не мешали мутациям)
если коротко - "Запомни текущее состояние браузера, чтобы потом восстановить"

1. 🔧 MUTATION:
🏗️ Меняет настоящий DOM:
- Placement: parentNode.appendChild(newElement)
- Update: element.className = 'new-class'
- Deletion: parentNode.removeChild(oldElement)
💅 Вызывает CSS хуки:
- useInsertionEffect callbacks (этот хук для библиотеки CSS in JS)
⚡ Особенности:
- DOM уже изменен ✅
- Браузер еще НЕ перерисовал экран ⏳
- События пока отключены 🔇
Если коротко - "Применяем все изменения к настоящему DOM прямо сейчас но не отрисовываем" 🛠️

2. 🔄 ПЕРЕКЛЮЧЕНИЕ ДЕРЕВЬЕВ:
🎯 Меняет указатели местами:
- root.current = finishedWork (WIP → current)
- Старое current становится alternate
- Никакого копирования - просто смена ссылок!
⚡ Происходит мгновенно:
- Одна строчка кода
🎮 Double Buffering в действии:
WIP был "черновиком" → стал "оригиналом"
Current был "оригиналом" → стал "черновиком"
Если коротко - "Показываем новое дерево вместо старого за 1 операцию" 🔄

3. 📐 LAYOUT:
🎯 Работает с готовым DOM:
- useLayoutEffect callbacks
- componentDidMount/componentDidUpdate
- componentDidCatch (Error Boundaries)
- ref callbacks получают элементы
📏 Может читать размеры:
- getBoundingClientRect() работает синхронно и вызывает Reflow принудительно. без getBoundingClientRect рефлоу произойдет позже
- Размеры уже посчитаны, но экран не обновлен
⚡ Синхронно до paint:
- Блокирует перерисовку браузера
Если коротко - "Читаем/пишем DOM синхронно перед показом пользователю" 📏

4. 🎨 PASSIVE:
⏰ Работает ПОСЛЕ paint:
- useEffect callbacks
- useEffect cleanup functions
- Пользователь уже видит обновленный экран ✅
🔄 В отдельном macrotask:
- Не блокирует отрисовку браузера
💡 Для side effects:
- API запросы
- Подписки на события
- Логирование, аналитика
- Всё что не влияет на layout
Если коротко - "Делаем асинхронную работу после того, как пользователь увидел изменения" 🎨


Классовые методы жизненного цикла

🟢 Основные (рекомендуемые):

constructor()
Когда: При создании компонента
Зачем: Инициализация state, привязка методов

render()
Когда: Каждый рендер (обязательный метод)
Зачем: Возвращает JSX для отрисовки

componentDidMount()
Когда: После первой отрисовки в DOM
Зачем: API запросы, подписки, таймеры

componentDidUpdate()
Когда: После каждого обновления (кроме первого)
Зачем: Реакция на изменение props/state

componentWillUnmount()
Когда: Перед удалением компонента
Зачем: Очистка (отписки, таймеры, запросы)

🔵 Современные статические:

static getDerivedStateFromProps()
Когда: Перед каждым рендером
Зачем: Синхронизация state с props

static getDerivedStateFromError()
Когда: При ошибке в дочерних компонентах
Зачем: Обновление state для показа fallback UI

getSnapshotBeforeUpdate()
Когда: Перед применением изменений к DOM
Зачем: Сохранение данных (scroll, focus) до мутаций

🟡 Проверки и ошибки:

shouldComponentUpdate()
Когда: Перед каждым обновлением
Зачем: Оптимизация - можно отменить ререндер

componentDidCatch()
Когда: При ошибке в дочерних компонентах
Зачем: Логирование ошибок, отправка в сервисы

🔴 Устаревшие (deprecated):

UNSAFE_componentWillMount()
Когда: Перед первым рендером
Зачем: Подготовка к рендеру (лучше использовать constructor)

UNSAFE_componentWillReceiveProps()
Когда: При получении новых props
Зачем: Обновление state (лучше использовать getDerivedStateFromProps)

UNSAFE_componentWillUpdate()
Когда: Перед обновлением
Зачем: Подготовка к обновлению (лучше использовать getSnapshotBeforeUpdate)

## error boundaries

Error Boundary - это компонент-обертка, который предназначен для отлова ошибок в компонентах внутри него. Реализуется только с помощью классового компонента.

За отлов отвечают 2 метода:

getDerivedStateFromError (статический) - выполняется в render фазе, может вызываться несколько раз, только возвращает новый state (например, hasError: true), никаких side effects. Аргумент: error
componentDidCatch - выполняется в commit фазе один раз, отвечает за side effects (логирование, аналитика). Аргументы: error и errorInfo
Error Boundary НЕ ловит: ошибки в event handlers, промисы, setTimeout/setInterval. Ловит только синхронные ошибки в React lifecycle методах.

в нексте есть встроенные еррор баундери. например на уровне страниц (файлы error.tsx) или на уровне всего приложения. для обычное реакта есть различные библитеки расширяющие возможности. которые хуки например добавляют. но под копотом они все равно используют классовый компоенент
