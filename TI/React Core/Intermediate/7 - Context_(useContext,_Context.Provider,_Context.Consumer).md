# Context (useContext, Context.Provider, Context.Consumer)

Context решает проблему передачи данных между компонентами. Мы можем создать контекст:

```ts
const Context = createContext(fallbackValue)
```

Context - объект, который возвращает Provider и Consumer. Consumer - старый способ получить контекст в компоненте. (ну и для классовых компонентов актуален) Provider - компонент-обертка. Он принимает проп value. В него нужно передать контекст, доступ к которому ты хочешь обеспечить изнутри. Потом в компонентах внутри этого Provider ты можешь вызывать useContext(Context) и получать к нему доступ.

fallbackValue используется когда компонент находится вне Provider - в этом случае useContext вернет именно это значение по умолчанию.

Context особенно полезен в компонент-композициях - когда нужно передать данные между "родительским" компонентом и его "детьми", не пробрасывая пропсы через промежуточные элементы. Это активно используется в UI библиотеках:

```ts
// Пример: Dropdown компонент
<Dropdown>
  <Dropdown.Trigger>Open menu</Dropdown.Trigger>
  <Dropdown.Content>
    <Dropdown.Item>Option 1</Dropdown.Item>
    <Dropdown.Item>Option 2</Dropdown.Item>
  </Dropdown.Content>
</Dropdown>

// Accordion, Modal, Tabs, Form - все работают по этому принципу
<Accordion>
  <Accordion.Item>
    <Accordion.Header>Title</Accordion.Header>
    <Accordion.Content>Content</Accordion.Content>
  </Accordion.Item>
</Accordion>
```

Внутри такие компоненты используют Context, чтобы Dropdown.Item мог общаться с родительским Dropdown, а Accordion.Content знал о состоянии Accordion.Item.

Оптимизация и лучшие практики
Provider сравнивает value обычным строгим сравнением через ===. Так что каждый заново созданный массив, объект или функция будет триггерить ререндер всех чайлдов. В Provider реализован механизм как в memo: если prevValue === value, то ререндера не будет. Bailout. Поэтому надо мемоизировать value.

Лучше создавать несколько мелких контекстов вместо одного большого. Держать контексты нужно как можно ниже, чтобы оборачивать как можно меньше чайлдов. причем контксты могут даже одним стейтом управлять. один на чтение другой на запись, если они оборачивают разные чайлды

Когда использовать Context
✅ Стоит использовать для:

Редко обновляемых данных (theme, locale, user)
Простых значений
Локальных областей UI (модалки, формы, compound components)
Конфигурации и настроек

❌ Не стоит использовать для:
Больших данных с частыми обновлениями
Сложной бизнес-логики
Много чайлдов, которые не используют контекст
Альтернативы
Как альтернатива для большого объема данных лучше использовать сторонние state менеджеры. Они хранят данные вне React fiber и не триггерят ререндер всех чайлдов, поэтому можно обернуть все приложение в провайдер. Типа Zustand или Redux.

Из минусов Context - при изменении контекста ререндерится все, что находится внутри его Provider.
